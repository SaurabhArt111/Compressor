# Image Compressor

A local-first batch image compressor. Drop in JPG/PNG/WebP/TIFF/GIF/BMP/AVIF/HEIC
files (or a whole folder) — including files in the 300–500MB range — pick a
target file size, and it finds the highest quality that still fits, entirely
on your own machine. Nothing is ever uploaded to the cloud.

- **Frontend:** React + Vite
- **Backend:** Node.js + Express + [Sharp](https://sharp.pixelplumbing.com/) (libvips)

## Quick start

```bash
npm install     # installs both client and server (npm workspaces)
npm run dev     # starts the backend (:5000) and the Vite dev server (:5173)
```

Open **http://localhost:5173**.

### Production

```bash
npm install
npm run build   # builds the React app into client/dist
npm start       # serves the API + the built frontend from :5000
```

Open **http://localhost:5000**.

Requires Node.js **18.17+**.

## What it does

1. **Drag & drop** images or an entire folder (folder structure is preserved
   end to end — upload, processing, and the downloaded ZIP all mirror your
   original folder layout).
2. **Pick a target size** — 10MB, 12MB, or a custom value.
3. **Compress.** Each image is searched for the highest quality that still
   fits under the target (see [the algorithm](#the-compression-algorithm)
   below), with live per-file progress.
4. **Compare** the original and compressed image with a before/after slider,
   and see the exact size, resolution, format, and quality used.
5. **Download** individual files or everything as a ZIP, with folder
   structure intact.

Every completed batch is recorded in **History**, and defaults (target size,
format, concurrency, quality bounds) live in **Settings**.

## The compression algorithm

For each image, `server/src/services/compressionEngine.js`:

1. **Already small enough?** If the source is already under the target, it
   tries one high-quality re-encode — but only accepts it if that re-encode
   is *also* no larger than the original (converting an already-compressed
   JPEG into another lossy format at very high quality can occasionally
   come out bigger). If re-encoding doesn't help, it keeps the original
   bytes untouched rather than "compressing" a file into something larger.
2. **Binary-search quality** at full resolution for the highest quality
   setting (1–100) whose encoded size still fits under the target. Sharp
   caches decode/resize work internally, so repeated encodes that only vary
   the quality knob are much cheaper than the first one.
3. **Resolution ladder.** If even the quality floor overshoots the target,
   it steps resolution down (100% → 90% → 80% … → 40%) and re-runs the
   quality search at each step, stopping at the first one that fits. This
   means resolution is only reduced when quality reduction alone can't
   reach the target.
4. **Honest fallback.** If nothing on the ladder reaches the target, it
   returns the smallest result found and reports `targetReached: false`
   rather than continuing to crush quality/resolution to force a match —
   exactly as requested: *if 10MB can't be hit without destroying quality,
   show the best result and say so clearly.*

**Format selection** (when set to "Auto"):
- Images that need transparency → **WebP** (lossy WebP keeps alpha; JPEG
  can't, and lossless PNG compresses far worse).
- Opaque photos → **AVIF** below ~6 megapixels, **WebP** above it. This
  threshold is deliberate: in testing, AVIF encoded the same image roughly
  **30× slower** than WebP (a 24MP photo: ~55s vs ~2s for one encode), and
  the search needs several encodes per image. Above the threshold, AVIF
  would turn a few-second compression into several minutes — exactly wrong
  for the large photos this tool targets. WebP still reaches very similar
  visual quality per byte.

All of this is exercised by real, generated-image tests — see [Testing](#testing).

## Efficient handling of very large files

- Uploads use `multer`'s **disk storage** (streamed straight to disk), never
  buffered in memory or passed through the browser as base64.
- Sharp/libvips **streams pixel data** rather than decoding a whole image
  into a JS buffer, so a 500MB TIFF doesn't need 500MB+ of Node heap.
- Before/after previews in the UI are small **on-the-fly thumbnails**
  generated by the server (`/api/download/:jobId/:fileId/thumbnail/:variant`)
  — the browser never receives the full-size original or compressed file
  just to render a preview.
- **Bounded concurrency**: you can pick how many files process in parallel
  (Settings → Concurrency), but the server also enforces its own hard
  ceiling (`MAX_SERVER_CONCURRENCY` in `server/src/config.js`, default 4)
  regardless of what's requested, so a batch of huge files can't spike RAM
  by all decoding at once.
- ZIP downloads are **streamed** via `archiver` directly to the HTTP
  response, not built in memory first.

## Testing

Two real test suites are included (no mocks — they generate actual images
and run the actual server):

```bash
cd server
npm test                        # compression engine tests (quality search,
                                 # format selection, transparency, fallback honesty)
node src/__test__/api.test.mjs  # full HTTP API: upload, compress, progress,
                                 # download, ZIP, history, cancellation
```

Note: the engine tests generate a real ~90MB TIFF fixture and run the actual
AVIF/WebP encoders, so a full run takes a few minutes.

## Configuration

Most tunables live in `server/src/config.js`:

| Constant | Default | Meaning |
|---|---|---|
| `PORT` (env var) | `5000` | Server port |
| `MAX_SERVER_CONCURRENCY` | 4 | Hard cap on parallel image jobs |
| `MAX_UPLOAD_BYTES` | 2GB | Per-file upload limit |
| `QUALITY_FLOOR_DEFAULT` / `_CEILING_DEFAULT` | 35 / 100 | Quality search bounds |
| `RESOLUTION_LADDER` | `[1, .9, .8, .7, .6, .5, .4]` | Downscale steps tried if quality alone can't reach target |
| `JOB_RETENTION_MS` | 24h | How long uploaded/compressed files stay on disk before cleanup |

If you change `PORT`, also set `SERVER_PORT` when running the client dev
server so its proxy points at the right place:

```bash
PORT=6000 npm run dev -w server
SERVER_PORT=6000 npm run dev -w client
```

## Troubleshooting

- **Sharp fails to install / "Could not load the sharp module"**: Sharp
  ships prebuilt binaries per-platform. Delete `node_modules` and
  `package-lock.json` and run `npm install` again on the target machine
  (don't copy `node_modules` between different OSes/architectures).
- **Large uploads time out on a slow network**: the server disables Node's
  default request/header timeouts (`server/src/index.js`) specifically so
  300–500MB uploads aren't cut off, but very restrictive proxies/firewalls
  in front of the server could still impose their own limits.
